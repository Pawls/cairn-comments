## Settled

- **Name.** Display name "Cairn Comments", npm package `cairn-comments`, extension id
  `pawls.cairn-comments-vscode` (the `pawls` publisher, 2026-10-07), CLI `cairn`. "cAIrn" is a logo treatment only. Two small Marketplace extensions already use
  "Cairn" (`valpet.cairn-extension`, 82 installs, AI task context; `fractaldecoder.cairn`,
  9 installs, Rust snapshots), so the bare name is not used for the listing.
- **No markers in committed code (2026-09-25).** Committed code is the owner's code with AI
  comments removed. Anchors (declaration, body hash, statement path) live in the sidecar.
  Moved into v1 as A12 to A16 because it changes the format v1 would publish. This
  replaces the old private-mode slices; what remains of them is B2.
- **No task graph.** Context keeping in the style of beads (and `valpet.cairn-extension`)
  is out of scope: it stores work state, not knowledge anchored to code.
- **Never hide code on disk.** Summaries steer agents at the tool layer (outline command,
  read hook). Eliding bodies through the filter breaks builds, tests, grep, and LSP, makes
  `clean` impure, and invites agents to reimplement the stub.
- **Summaries guide navigation; source guides edits.** An agent reads a function's source
  before changing it.

### B2 — Comments outside the branch · Opus 5.5 / medium {#b2}

**Status:** Not started. What was left of private mode once v1 dropped markers: the code
is already clean, so the question is only where the sidecar lives.

Visible change: in a team that wants no trace at all, `cairn init --private` leaves the
branch byte-identical to a repo without the tool, and the owner can still share comments
with a teammate or a cloud agent who opts in.

- [ ] `init --private` writes only untracked config: filter settings in `.git/config`,
      attributes in `.git/info/attributes`; the team's `.gitattributes` is byte-identical
      after init (integration test, both `autocrlf`).
- [ ] Sidecars go to a separate ref, `refs/cairn/comments`, instead of the working tree:
      a tree of the same markdown files, committed by `sync` with plumbing
      (`hash-object`, `mktree`, `commit-tree`, `update-ref`), so nothing touches the index
      or the branch. The filter reads bodies from that ref.
- [ ] Sharing is opt-in: `cairn push` and `cairn fetch` move the ref; a clone without it
      simply has no comments. Merging two sides of the ref reuses the `merge-sidecar`
      driver's logic.
- [ ] `check` works the same in both storage modes; `cairn init --private --migrate`
      moves tracked sidecars into the ref.
- [ ] Verify: `npm test`; a cloud-agent style fresh clone with `cairn fetch` smudges the
      same comments as the owner's worktree.

Kill criteria: if updating a ref from inside `sync` races with git's own ref locks during
commit (the pre-commit hook runs mid-commit), fall back to sidecars under
`.git/cairn/comments/` with no sharing, and record why.

### B3 — Benchmark harness: do comments and summaries pay? · Opus 5.5 / high {#b3}

**Status:** Not started. Widened on 2026-09-25 from "measure summary value" to also
measure AI comments themselves, since the same harness answers both. A token saving
cannot be observed in a single real session (it is counterfactual), so paired runs are
the only honest source for the number. The **none** and **comments** arms can run before
v1 publishes and alongside A12 to A16: an agent worktree reads the same in marker and
markerless mode.

Visible change: `docs/benchmark.md` records the method and results, and the README can
state a measured token and time difference, with its spread, instead of a claim.

- [ ] Method in `docs/benchmark.md`:
      - Harnesses: Pi and `claude -p --output-format stream-json`, same model. Hermes is
        out: its persistent memory would carry answers between runs. Pi has no Cairn
        hook adapter, so its runs test the filter alone.
      - No memory between runs: each Claude run gets a fresh `CLAUDE_CONFIG_DIR` (no
        user CLAUDE.md, auto memory, skills, or hooks from the owner's setup) and API
        key auth; each Pi run a fresh session and config. The repo's own AGENTS.md is
        part of the start state and identical in every arm.
      - Arms, all from the same commit: **none** (the committed code, no smudge),
        **comments** (smudged agent worktree), later **summaries** (comments plus hand
        written outlines) for the B4 to B6 decision.
      - Comments written once at the base commit by a separate agent session that never
        sees the tasks, then frozen, so no comment can leak an answer.
      - Tasks: 8 to 10 from real history on this repo and one external repo, each a
        commit whose parent is the start state: bug fixes, small features, and pure
        questions (no edit). Success is the commit's own tests passing, or a written
        answer key for questions.
      - At least 5 runs per task per arm, fresh worktree each run, arm order randomized,
        temperature fixed where the harness allows.
- [ ] Capture that works for any harness: a local recording proxy between the harness
      and the provider API logs each response's usage (input, output, cache read, cache
      write) and tool calls. Where a harness also writes its own session log, compare
      totals against the proxy once to confirm them.
- [ ] Per run: input tokens (uncached and cached separately), output tokens, turns, tool
      calls by kind, distinct files read, wall time, cost, success. Report median and
      IQR per arm and the paired per-task difference; also the comment tokens delivered
      (the overhead side).
- [ ] Results recorded in `docs/benchmark.md` and summarized here with the go/no-go.

Kill criteria: if the **comments** arm is not better than **none** on tokens or success,
stop and rethink the product claim before publishing (v1 A9). If **summaries** save under
20% of tokens over **comments** on the question tasks, strike B4 to B6.

### Follow-ups from the deslop plan (archived)

Moved here when [the deslop plan](archived/deslop.md) was archived, 2026-10-07.

- **`ScannedComment` as a union on `style`** (from D2). `literal` is set only when `style === "string"`; a
  union would remove the `c.literal!` in `convertDemoted`. It changes an exported type, so it waits until no
  lane is open.
- **CRLF lost when the stripped file has no terminator at all** (from D8; on `main` before it too). With one
  unterminated code line, or no code, placed comments fall back to LF: `#~ note\r\npass` comes back as
  `#~ note\npass`. design.md § Known gaps covers only the comment-only file. The fix records the comment's own
  terminator, which is new sidecar metadata, so it is a slice of its own, test first.
- **A promote can drop an entry the extension has not seen yet** (from D10, unverified). `SidecarStore` caches
  a sidecar's disk copy until the watcher fires; an in-process promote run before that would write the
  sidecar without an entry an agent had just added, losing the comment. Nothing tests it.
- **The late sidecar event behind D9's two `settle(1_500)` guards** (from D6). A reset that waits for the file
  watcher did not remove it (5 of 20 against 4 of 20, reverted). Suspect, untested: `trackDocuments` in
  `extension.ts` calls `sidecarChanged` from `onDidCloseTextDocument` for a sidecar buffer, and VS Code closes
  sidecar buffers that have no tab lazily.
- **The review-suite promote returning `undefined`** (D5's one Windows failure) reproduced on `main` in WSL at
  2 of 20 and 0 of 40 with the review repository's git extension off (D6). Suggestive only; the swallowed CLI
  error (next item) is still what would show the cause.
- **`native/competitor/extension.cjs`** (the stand-in paste provider) was outside every slice's Touches and
  has not been read for these rules.
- **Confirm pass in BoxelBuilderExperiment** (from D10): 11 of its 23 entries are stale after the hash rule
  changed; each wants a Confirm, or a check that it is still true.
- **Make a failed CLI run in the extension visible to tests** (from D5). `runOnFile` shows the error as a
  notification and returns `undefined`, so an e2e failure on that path cannot show its cause. Log it to the
  console as well. This is what would explain the one Windows failure if it recurs.
- **A unit-test seam for the extension** (from D5). Every extension module imports `vscode`, so only the e2e
  and native suites cover `activate` and the review tree. A small `vscode` mock for vitest, or the pure parts
