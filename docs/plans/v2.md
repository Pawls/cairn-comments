## Settled

- **Name.** Display name "Cairn Comments", npm package `cairn-comments`, extension id
  `pawls.cairn-comments-vscode` (the `pawls` publisher, 2026-10-07), CLI `cairn`. "cAIrn" is a logo treatment only. Two small Marketplace extensions already use
  "Cairn" (`valpet.cairn-extension`, 82 installs, AI task context; `fractaldecoder.cairn`,
  9 installs, Rust snapshots), so the bare name is not used for the listing.
- **No markers in committed code (2026-09-25).** Committed code is the owner's code with AI
  comments removed. Anchors (declaration, body hash, statement path) live in the sidecar.
  Moved into v1 as A12 to A16 because it changes the format v1 would publish. This
  replaces the old private-mode slices; what remains of them is B2.
- **No task graph.** Context keeping in the style of beads (and `valpet.cairn-extension`)
  is out of scope: it stores work state, not knowledge anchored to code.
- **Never hide code on disk.** Summaries steer agents at the tool layer (outline command,
  read hook). Eliding bodies through the filter breaks builds, tests, grep, and LSP, makes
  `clean` impure, and invites agents to reimplement the stub.
- **Summaries guide navigation; source guides edits.** An agent reads a function's source
  before changing it.

### ~~B2 — Comments outside the branch~~ · Opus 5.5 / medium — SHIPPED 2026-10-09 {#b2}

**Status:** Done on branch `private-comments` (2026-10-09). What was left of private
mode once v1 dropped markers: the code is already clean, so the question is only where the
sidecar lives.
**Touches:** `packages/core/src/{store,index}.ts` (new `store.ts`), `packages/cli/src/{files,check,scan,init,main,git}.ts`,
a new `packages/cli/src/share.ts`, `packages/vscode/src/{sidecars,extension,reviewTree}.ts`, `packages/vscode/e2e/`
(a `private` suite), design.md § Decisions and a new § Private mode, the READMEs.
**After:** none.

Decided 2026-10-09 (owner): the sidecars stay plain markdown files, in
`<git common dir>/cairn/comments/`, and `refs/cairn/comments` is only how they travel. A ref
as the store, which this slice first planned, would have broken the extension's file-based
editing: a paste that moves a comment and Promote/Demote write the source and its sidecar
as one `WorkspaceEdit`, so a single Ctrl+Z undoes both, and nothing can undo a ref update.
It would also have cost several git processes per `sync`, some inside the pre-commit hook.
Every worktree shares the common dir, so agent worktrees read one copy.

Visible change: in a team that wants no trace at all, `cairn init --private` leaves the
branch byte-identical to a repo without the tool, and the owner can still share comments
with a teammate or a cloud agent who opts in.

- [x] Private mode is on when `<git common dir>/cairn/comments/` exists, which both the CLI
      and the extension can test without starting git. One resolver in core gives each
      source's sidecar file, and every read and write goes through it: the filter, `sync`
      and the commands built on it, `scan` (its ignore file moves too), `check`.
      `packages/core/src/store.ts`; the CLI caches it per process (`sidecarLocation` in
      `files.ts`).
- [x] `init --private` writes only untracked config: filter settings in `.git/config`,
      attributes in `.git/info/attributes`, adapter settings files in `.git/info/exclude`;
      the team's `.gitattributes` is byte-identical after init (integration test, both
      `autocrlf`). The pre-commit hook stages nothing of the tool's. `init` keeps the mode
      a repository already has.
- [x] `check` works the same in both storage modes; `init --private` refuses while tracked
      sidecars exist, and `init --private --migrate` moves them into the store and stages
      their removal along with the tool's `.gitattributes` lines.
- [x] Sharing is opt-in: `cairn push [remote]` commits the store to `refs/cairn/comments`
      with plumbing and pushes it; `cairn fetch [remote]` fetches the ref and merges it into
      the store by entry with the `merge-sidecar` driver's logic. A clone without the ref
      simply has no comments. Built with a scratch index (`update-index --index-info`,
      `write-tree`) instead of `mktree`, which would take a process per folder.
- [x] The extension finds sidecars in the store: the overlay, the watcher, and the edit
      actions. The `private` e2e suite (`packages/vscode/e2e/private.test.ts`) covers the
      overlay, a write from outside, Edit, and Ctrl+Z after Promote restoring both files.
- [x] Verify: `npm test`; `npm run test:vscode`; a cloud-agent style fresh clone with
      `cairn fetch` smudges the same comments as the owner's worktree.
      2026-10-09: `npm test` 543 on Windows and WSL Ubuntu, lint clean. `npm run
      test:vscode` 35 overlay + 4 private + 9 review on WSL; on Windows 35 + 2 + 9 before the
      last two private tests were added, then the private suite alone 4/4. Later Windows
      runs failed one overlay test, the stale list, because git could not start inside the
      test window (exit 0xC0000142, `STATUS_DLL_INIT_FAILED`, a process-creation limit on
      the machine at the time; that code path is unchanged by this slice). The fresh-clone
      scenario is "gives a fresh clone the owner's comments only after fetch" in
      `packages/cli/test/private.test.ts`. Every new test was red first, or
      mutation-checked when it passed on its first run (the private `check`, the same-file
      merge, all four private e2e tests). `npm run bench`: process checkout 3,253 ms
      against 3,225 to 3,246 ms on B8, warm status 51 ms, so the per-process store lookup
      costs nothing measurable.

Kill criteria: if two worktrees writing the shared store at once lose entries in practice,
add a lock around sidecar writes in private mode; if that cannot be made reliable on
Windows, keep one store per worktree and record why.

### B3 — Benchmark harness: do comments and summaries pay? · Opus 5.5 / high {#b3}

**Status:** Not started. Widened on 2026-09-25 from "measure summary value" to also
measure AI comments themselves, since the same harness answers both. A token saving
cannot be observed in a single real session (it is counterfactual), so paired runs are
the only honest source for the number. The **none** and **comments** arms can run before
v1 publishes and alongside A12 to A16: an agent worktree reads the same in marker and
markerless mode.

Visible change: `docs/benchmark.md` records the method and results, and the README can
state a measured token and time difference, with its spread, instead of a claim.

- [ ] Method in `docs/benchmark.md`:
      - Harnesses: Pi and `claude -p --output-format stream-json`, same model. Hermes is
        out: its persistent memory would carry answers between runs. Pi has no Cairn
        hook adapter, so its runs test the filter alone.
      - No memory between runs: each Claude run gets a fresh `CLAUDE_CONFIG_DIR` (no
        user CLAUDE.md, auto memory, skills, or hooks from the owner's setup) and API
        key auth; each Pi run a fresh session and config. The repo's own AGENTS.md is
        part of the start state and identical in every arm.
      - Arms, all from the same commit: **none** (the committed code, no smudge),
        **comments** (smudged agent worktree), later **summaries** (comments plus hand
        written outlines) for the B4 to B6 decision.
      - Comments written once at the base commit by a separate agent session that never
        sees the tasks, then frozen, so no comment can leak an answer.
      - Tasks: 8 to 10 from real history on this repo and one external repo, each a
        commit whose parent is the start state: bug fixes, small features, and pure
        questions (no edit). Success is the commit's own tests passing, or a written
        answer key for questions.
      - At least 5 runs per task per arm, fresh worktree each run, arm order randomized,
        temperature fixed where the harness allows.
- [ ] Capture that works for any harness: a local recording proxy between the harness
      and the provider API logs each response's usage (input, output, cache read, cache
      write) and tool calls. Where a harness also writes its own session log, compare
      totals against the proxy once to confirm them.
- [ ] Per run: input tokens (uncached and cached separately), output tokens, turns, tool
      calls by kind, distinct files read, wall time, cost, success. Report median and
      IQR per arm and the paired per-task difference; also the comment tokens delivered
      (the overhead side).
- [ ] Results recorded in `docs/benchmark.md` and summarized here with the go/no-go.

Kill criteria: if the **comments** arm is not better than **none** on tokens or success,
stop and rethink the product claim before publishing (v1 A9). If **summaries** save under
20% of tokens over **comments** on the question tasks, strike B4 to B6.

**Status:** Done on branch `node-free` (2026-10-09). Setup and repair used to stop with an
install link when `node` 22+ was missing; this slice removes the requirement for extension users.
Wanted before the Marketplace listing drops its Preview badge.
**Touches:** `packages/core/src/home.ts`, `packages/cli/src/init.ts`, `packages/vscode/src/{runtime,setup,review}.ts`

design.md § Packaging, the READMEs' requirement lines.
**After:** none.

Measured 2026-10-07 (Windows, VS Code 1.140, ten one-shot `clean` runs on
`packages/core/src/lines.ts`): `ELECTRON_RUN_AS_NODE=1 Code.exe <home>/main.js` took 69 ms
per run against 76 ms for `node`, with byte-identical output; the runtime reports Node 24.21.
Every Electron run also printed a crashpad `CreateFile` error line to stderr, which git
would show on every filtered command. `Code.exe` sits at a stable path; each version's
files live in a hashed folder beside it.

Visible change: on a machine with no Node, **Set Up Cairn Comments in This Repository**
works, and git status, diff, and commit in a terminal still filter.

- [x] Spike: silence the crashpad line without hiding real stderr (an Electron switch or
      environment variable, else a launcher that drops only that line). Record what works.
      2026-10-07: the line is not Electron's own. A process started from VS Code inherits
      `CHROME_CRASHPAD_PIPE_NAME`, and that pipe can be stale: here it named the crashpad
      handler of pid 6020, long gone, while the live handlers had other pipes. Electron run
      as Node tries the pipe, fails, logs the line to stderr, and appends it to `debug.log`
      in the editor's install folder. With the variable unset (or a clean environment, as
      in a terminal outside VS Code) there is no line and no `debug.log` write; stderr and
      exit codes from the script pass through unchanged. No Electron switch or
      `ELECTRON_*` variable helped (`ELECTRON_ENABLE_LOGGING`, `ELECTRON_LOG_FILE`,
      `ELECTRON_NO_ATTACH_CONSOLE` all still print it). So the launcher unsets that one
      variable before it starts the editor runtime.
- [x] Spike: where the runtime lives for VS Code, Insiders, Cursor, and Windsurf on Windows,
      macOS, and Linux (deb, rpm, Snap, tarball), and in VS Code Server (WSL, SSH,
      containers: `~/.vscode-server/bin/<commit>/`, replaced on every update). Which paths
      survive an update.
      2026-10-07, measured on Windows and WSL; the rest is from each product's install
      layout, unverified. The extension host's `process.execPath` is the runtime, so the
      extension records that rather than guessing per product.
      - Windows (VS Code 1.140 user install): `%LOCALAPPDATA%\Programs\Microsoft VS
        Code\Code.exe`, stable across updates; each version's files sit in a hashed folder
        beside it (`2a59476c9b\`). Insiders, Cursor, and Windsurf install the same way under
        their own folders. Node 24.21.
      - WSL (VS Code Server): `~/.vscode-server/bin/<commit>/node`, a real Node (24.21). An
        update installs a new commit folder and removes the old one; only one was present.
        Newer servers may use `~/.vscode-server/cli/servers/Stable-<commit>/server/node`.
        Cursor and Windsurf use `~/.cursor-server`, `~/.windsurf-server`. Not stable, so the
        launcher looks for the same file in a sibling commit folder when the recorded one
        is gone.
      - macOS: the extension host runs `Code Helper (Plugin)` inside the app bundle, which
        an update replaces in place. Stable.
      - Linux deb and rpm: `/usr/share/code/code`, stable. Snap:
        `/snap/code/<revision>/usr/share/code/code`; the extension records
        `/snap/code/current/...` instead. Tarball: wherever the user unpacked it.
      - An editor can turn Electron's `RunAsNode` fuse off, and then its binary would open a
        window instead of running the script. The extension checks before recording:
        `ELECTRON_RUN_AS_NODE=1 <runtime> --version` prints `v24.21.0` with the fuse on.
        Run as the editor instead (the variable unset, which is what a fuse that is off
        amounts to), `Code.exe --version` printed nothing on Windows and exited 0, so the
        check rejects it either way.
      - Shells: git runs the filter, merge driver, and hooks through sh on every platform
        (Git for Windows ships one), and Claude Code runs hooks through Git Bash. Cursor
        runs hook commands through PowerShell on Windows and Codex through the native
        interpreter, and neither can run an sh script. A `.cmd` launcher fails the other
        way: run from git's sh with a space in its path and arguments after it, cmd reparses
        the line and splits the path. So agent hooks on Windows keep
        `node "<home>/main.js"` and still need Node (Claude Code's included: it can be set

      - Order: the launcher tries `node` from PATH first, so machines with Node behave as
        before. Telling a too-old Node apart costs a version probe on every git command, so
        the home's `main.js` checks its own runtime instead and, when the launcher started
        it, exits with a reserved code that sends the launcher on to the editor runtime.

      to the home on activation. `init` and repair keep working on machines with Node.
      Built as design.md § Packaging, "Running without Node", describes. The extension now
      runs its own CLI calls on its runtime through `execFile`, so `shellQuote` and its

- [x] The extension refreshes that runtime path on every activation; repair covers a

      `packages/cli/test/launcher.test.ts` (six cases, the VS Code Server sibling and the

### Follow-ups from the deslop plan (archived)

- **`ScannedComment` as a union on `style`** (from D2). `literal` is set only when `style === "string"`; a

  lane is open.
- **CRLF lost when the stripped file has no terminator at all** (from D8; on `main` before it too). With one
  unterminated code line, or no code, placed comments fall back to LF: `#~ note\r\npass` comes back as
  `#~ note\npass`. design.md § Known gaps covers only the comment-only file. The fix records the comment's own
  terminator, which is new sidecar metadata, so it is a slice of its own, test first.

  a sidecar's disk copy until the watcher fires; an in-process promote run before that would write the
